A2A、MCP、Hub 怎麼選:省工的分層方法論

直接打 A2A、經過 MCP、還是走 Hub——底層都是同一件事:Agent 問資料。這頁講三件事:四個檔位的取捨、現實為什麼是一團野蠻生長的網,以及最關鍵的——怎麼在不逼一百個老系統改一行的前提下,讓 Hub 幫你省工。核心一句:讓 Hub 適應葉子,不是葉子適應 Hub。

🎚️ 四個檔位:同一條線,不是四選一

不是四選一,是同一個「Agent 問資料」動作、你要多少紀律的四個檔位。往右一格,多一分治理、少一分直接。箭頭上的字,是「什麼情況才該往上爬」。

檔位用意取捨(得 / 付)老 pattern
裸接零基建最快,只適合一次性 spike得:立刻能動 / 付:N×M、無授權無稽核SQL 寫進畫面
A2A後端自描述+標準化,一個 A2A 全體重用得:可重用、藏醜 legacy / 付:多層維護、授權各自管Adapter + Repository
MCP一個域的統一入口 + 最低發現/授權得:一點連線拿一組能力 / 付:多一跳、MCP 會長很多個一組 Controller 路由
HubMCP 多了要統籌:身分/policy/目錄/稽核集中得:唯一真相、跨系統可治理 / 付:又一跳、新單點、要建控制面Front Controller / API Gateway

🌿 現實不是乾淨的分層:野蠻生長 + 混雜

上面那張是心智模型——現實長出來的是這張。層界會糊掉、東西會一直長:同一種「層」出現在不同地方、包著不同東西,而且常常是被組織需求(某個長官一句話)推出來的。

1A2A 野蠻生長數量會爆
一個 DB 就能長 20~30 個 A2A,各系統自己長、沒人統一攔。真實數量是幾千,不是幾十——這正是為什麼需要一個「目錄」。
2MCP 沒有固定形狀層界糊掉
一個 MCP 可能只是串一堆 raw API、可能收一堆 A2A、也可能混著兩種。「MCP 是一層」是簡化——它其實是「把一組能力收成工具面」這件事,發生在很多不同位置。
3Hub 常是「被推出來」的組織驅動
不是規劃好的頂點。常常是某個長官一句話,為了一個需求就開一個 Hub 點,底下建個 MCP 把 API 收上去。於是 Hub 不只一個,有正規的、也有臨時長出來的(圖中紅色虛線那顆)。

🪶 省工方法論:讓 Hub 適應葉子,不是葉子適應 Hub

關鍵陷阱:如果為了讓 Hub 能治理,就去逼每個 A2A 宣告憑證格式、接身分下傳、配合 Hub 的規矩——那你不是省工,是把工攤給一百個葉子。省工的來源,是反過來:把所有不對稱的適配都吞進 Hub 這一層,讓葉子維持它本來薄薄的樣子。

1不對稱原則:工往 Hub 集中,葉子零改動閘道厚、後面薄
A2A / API 維持它本來的授權方式(服務帳號 / API key / 自己的登入),一行不改,也不用知道 Hub 存在。憑證放 Hub 保管庫、在出口注入——葉子收到的還是它本來認得的那組帳號。你原本的 stateless gateway 直覺就是這個:閘道厚一點,讓後面全部維持薄。
2宣告在 Hub,不在葉子要求往上帶
「這個端點要什麼憑證、給誰用」是上架時記進 Hub 的目錄(六步上架表),不是叫 A2A 自己去寫卡。那筆 metadata 是 Hub 的資產,不是葉子的作業。Hub 一次學會門檻,之後不用每次跳下去問。
3預設粗粒度,細粒度 opt-in別逼老系統做 per-user
Hub 只管「哪個大佬能連哪個 A2A」(系統 / 端點級)。連上後,A2A 用它本來的服務帳號回。絕不預設逼老系統做 per-user 身分下傳(OBO)。只有少數「本來就支援身分、又真的需要 row-level」的系統,才個別開 OBO——例外,不是預設。
4把代價講白:粒度 = 工,你按系統挑沒有又省工又細粒度
粗:省工 + 葉子零改動 + 但那個大佬看得到整個系統。細:A2A / 系統要配合身分 + 對得起內稽,但很貴,而且需要葉子天生支援身分——30 年老系統多半沒有。所以逐系統挑,不是全域一刀切。
授權粒度葉子要做的事你換到什麼適合
粗(service,預設)零改動,用本來的服務帳號省工;但連上就看得到整個系統30 年 IBM 等做不了現代身分的絕大多數
細(obo,opt-in)要接身分下傳、跑 row-level 授權對得起內稽;但很貴、只有支援身分的系統做得到財務 / 人事等高敏、且本來就有身分機制的少數
一句話收:你省的工,是「不逼一百個葉子改」;你付的,是「預設粗粒度」。這是唯一誠實的省工法——把不對稱的適配都吞進 Hub,讓每個葉子當它不知道 Hub 存在。至於「Hub 隔兩層怎麼知道葉子的授權?」——它不知道、也不需要知道:門檻在上架時往上帶一次(metadata),真相留在葉子自己守(它本來就會)。Hub 從不跳兩層下去問。

🧰 那每層實際寫什麼 code?

很多人卡在「Hub / MCP 到底要寫什麼」。答案會讓你安心:每層要寫的東西是反過來的——真功夫全在 A2A,上面兩層本來就幾乎不用你寫 domain code。這正是省工的來源。

層你實際寫什麼性質每個系統要重寫嗎
A2AAgent Card + 查詢 handler + 對後端的服務帳號 auth真 domain code✅ 每系統一份(真功夫在這)
MCP薄殼 + list/describe/find/query 四個通用工具 + 一份註冊表殼寫一次;加系統 = 加資料❌ 殼共用,只加註冊資料
HubSSO 設定 + policy 規則 + 目錄 DB + 憑證庫 + 稽核設定 + 規則 + 資料,近乎零 domain code❌ 用「組」的,加系統 = 登記一筆
AA2A —— 唯一真的要寫 code 的地方厚
Agent Card(能力 + 授權宣告)、查詢 / 執行 handler、對老系統的服務帳號。domain 邏輯全在這,每個系統一份。你若只知道「A2A 要寫這些」,那不是懂得少,是抓對了重點。
MMCP —— 它空,是因為它本來就該空薄
不是 domain 邏輯,是一個協議薄殼 + 四個通用工具(list/describe/find/query,寫一次全系統共用)+ 一份「掛了哪些 A2A/API」的註冊表。這就是「導向型 gateway」那一類——加一個系統只是在註冊表加一筆,不是寫新 code。
HHub —— 是「組」的,不是「寫」的組裝
身分接 SSO(現成 library,設定)、目錄是一個 DB(存 metadata,你登記資料)、授權用現成 policy engine(你寫規則,不是 code)、憑證庫、稽核 log。你的工 = 設定 + 登記幾筆 + 寫幾條 policy。
一句話自檢:如果你發現 MCP 或 Hub 裡要寫一堆「這系統怎麼查、那欄位怎麼授權」的 per-system 邏輯——你做錯了,那些邏輯屬於 A2A。MCP / Hub 越薄、越像「設定 / 資料」而不是「程式」,你就越省工。這正是「Hub 適應葉子、葉子零改動」的另一面:工全壓在 A2A(domain)+ 註冊資料,不散到上面兩層。

身分 / 授權 / 目錄 / 稽核集中在 Hub;A2A wrapper 薄、零改動,由各系統自己長。既有系統與其使用者完全不動。授權兩道閘:Hub 粗閘(ABAC)+ 系統擁有者背書;憑證永不進 AI 客戶端,在 Hub 出口注入。

🏛️ 其實這就是 Agent 版的 MVC

你不是在發明新東西——當年軟體從「SQL 寫進畫面」走到 MVC、Front Controller、API Gateway;現在 Agent 存取資料,用新名字重跑同一條路。

Agent 時代古典 pattern負責什麼
舊系統 / 資料庫Model資料本身(很多異質後端 = 很多 Model)
A2AController(Adapter + Repository)轉接醜介面、給乾淨存取口(很多 A2A = 很多 Controller)
MCP server一組 Controller 的路由把一個域的能力收成統一工具面
HubFront Controller / API Gateway單一入口、集中授權 / 路由 / 記錄
消費端 AgentView / Client把資料組成使用者要看的答案

🎯 該停哪格:規模 × 必要性

越高不是越好。每往上一格拿「直接」換「治理」——爬多高,由你的規模乘以必要性決定。

1一次性探索 / spike→ 裸接
零基建最快,別為它蓋基礎建設。
2單一系統要給 Agent 用→ A2A
包成自描述介面,終結 N×M,一個 A2A 全體重用。
3一個域 / 團隊要管理性→ MCP
統一工具面 + 最低發現/授權/限流,AI 工具插上就用。
4集團級、多個 MCP、要治理→ Hub
把橫切關注集中,單一入口跨全系統,新增系統只是註冊。
兩個方向都是錯後果
規模到了還在裸接技術債:N×M 遲早爆,而且沒人查得到是誰動了資料
MCP 才一個就蓋 Hub過度設計:控制面的維運成本養不回來

一句話:你當然可以直接打 A2A——就像你當然可以 new 一個 Controller 直接問 DB,能動。問題從來不是「能不能」,是規模化之後誰管授權、誰查得到是誰動了資料、上百個系統 ×N 個 agent 的 N×M 誰來收拾。
